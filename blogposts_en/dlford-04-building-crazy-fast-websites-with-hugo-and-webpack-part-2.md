Webpack separates the code based on how it&rsquo;s used, which helps to reduce unused code and speed up page load times because the bundles are smaller, it&rsquo;s also much faster to download one file than all the individual bits that would be used on a page separately. We&rsquo;ll also use Babel to ensure your code will run in browser, this means we can use some newer JavaScript features that haven&rsquo;t made it to the browsers yet, and Babel will transpile that code to make it compatible. Lastly, we will use Webpack for cache-busting in production builds, this way we can set all CSS/JS files to cache forever, when the file changes the filename will also change, so the browser will only download files that have changed since the last visit.</p>&#xA;<p>Here is the GitHub branch for this completed segment:</p>&#xA;<p></p>&#xA; <a class=&#34;title&#34; href=&#34;https://github.com/dlford/hugo-webpack-demo/tree/part-2&#34; target=&#34;_blank&#34; rel=&#34;noopener noreferrer&#34;>GitHub - dlford/hugo-webpack-demo at part-2</a><p class=&#34;description&#34;>Example repository for my Hugo and Webpack series. Contribute to dlford/hugo-webpack-demo development by creating an account on GitHub.</p>&#xA;<h3 id=&#34;install-packages&#34;>Install Packages</h3>&#xA;<p>We&rsquo;re going to install a lot here, so let&rsquo;s run the command and you can read about it while they install:</p>&#xA;<p></p><code>Command Line</code><p></p>&#xA;<pre><code>npm install \&#xA; webpack \&#xA; webpack-cli \&#xA; webpack-dev-server \&#xA; babel-loader \&#xA; css-loader \&#xA; file-loader \&#xA; html-loader \&#xA; sass-loader \&#xA; yaml-loader \&#xA; react \&#xA; react-dom \&#xA; @babel/cli \&#xA; @babel/core \&#xA; @babel/plugin-transform-runtime \&#xA; @babel/preset-env \&#xA; @babel/preset-react \&#xA; @babel/runtime \&#xA; mini-css-extract-plugin \&#xA; sass \&#xA; autoprefixer \&#xA; postcss-cli \&#xA; postcss-loader \&#xA; postcss-nested \&#xA; postcss-normalize \&#xA; postcss-preset-env \&#xA; concurrently \&#xA; dotenv</code></pre>&#xA;<p></p><p>So, we&rsquo;ve got <code>webpack</code> of course, and its command line tool <code>webpack-cli</code>, <code>webpack-dev-server</code> we will use to proxy the Hugo site in development mode, and all the <code>*-loader</code> packages are used by Webpack for loading different file types. We have <code>react</code> and <code>react-dom</code> for pages that will use React. We have Babel and a bunch of plugins for it. We have Sass, Autoprefixer, and PostCSS for handling CSS files. Concurrently we&rsquo;ll use to start up Webpack and Hugo at the same time. Lastly, <code>dotenv</code> is used to read <code>.env</code> files for keeping secrets safe.</p>&#xA;<h3 id=&#34;how-webpack-and-hugo-interact&#34;>How Webpack and Hugo Interact</h3>&#xA;<p>Hugo gives each page a &ldquo;Kind&rdquo; and &ldquo;Type&rdquo;, we can use those as generic selectors for CSS and JS files. For example, if kind is &ldquo;page&rdquo; and type is &ldquo;blog&rdquo;, we can create a <code>main.js</code> file in <code>src/kind/page/blog/main.js</code> that will apply to all pages that match the same kind and type.</p>&#xA;<p>We can also get specific and create files such as <code>src/path/sitemap/main.js</code>, which would apply to the <code>/sitemap</code> page.</p>&#xA;<p>The same concepts apply for CSS files, where we can use <code>@import</code> to group re-usable CSS files together.</p>&#xA;<p>In Hugo, we can then inject those bundles into the HTML with link and script tags. In production builds, Webpack will output bundles as files into the <code>assets/generated</code> directory, we will check if the files exist and add them to the HTML conditionally, but in development mode there isn&rsquo;t an easy way to do this because the bundles are served over the Webpack dev server (HTTP), so we&rsquo;ll just add them whether they exist or not, this isn&rsquo;t really an issue in development.</p>&#xA;<p>If this sounds confusing, don&rsquo;t panic! There will be examples down below.</p>&#xA;<h3 id=&#34;folder-structure&#34;>Folder Structure</h3>&#xA;<p>Let&rsquo;s make a directory called <code>src</code> in the root of the project, anything in this folder should only be consumed by Webpack. This keeps things separate from Hugo file structure. Inside of <code>src</code> we can make new folders for different file types like <code>js</code> and <code>css</code>, as well as two special folders called <code>kind</code> and <code>path</code>.</p>&#xA;<p>The <code>kind</code> folder has to do with Hugo page types, here we can put CSS and JS files that apply to all pages of that specific type. The <code>path</code> folder will mimic URL paths to apply CSS and JS files to specific pages.</p>&#xA;<p>In both the <code>kind</code> and <code>path</code> folders, we&rsquo;ll have two types of files: <code>main</code>, and <code>critical</code>. The <code>main</code> CSS and JS files will be lazy loaded, and the <code>critical</code> CSS and JS files will be eager loaded when the page is visited. This allows fine-grained control on how each page loads its resources.</p>&#xA;<p>The end result will look something like this:</p>&#xA;<p></p><code>Directory Structure</code><p></p>&#xA;<pre><code>src&#xA; js&#xA; lazyload.js&#xA; ...&#xA; css&#xA; global.css&#xA; ...&#xA; kind&#xA; home&#xA; page&#xA; main.css&#xA; critical.css&#xA; main.js&#xA; critical.js&#xA; ...&#xA; path&#xA; sitemap&#xA; critical.css&#xA; ...</code></pre>&#xA;<p></p><p>We&rsquo;ll get more into this later, but for now let&rsquo;s move <code>assets/global.css</code> to <code>src/css/global.css</code>, and <code>assets/lazyload.js</code> to <code>src/js/lazyload/js</code>.</p>&#xA;<h3 id=&#34;configure-webpack&#34;>Configure Webpack</h3>&#xA;<p>Webpack can be pretty complex to configure, we have to hook it up to Sass, PostCSS, Babel, and other tools so it will act as a sort of hub for all of it.</p>&#xA;<p>First, we need to set up Babel, the <code>.browserslistrc</code> file tells Babel what browsers to support when transpiling code, this file also affects CSS transformation in other tools, you can learn more about this syntax in the <a&#xA;
